### Finding 1 (absolute `source.paths`) — ELEVATE to a serious, pre-s08 item, not a routine follow-up

CC frames it as "worth a named follow-up if `source.paths` is ever expected to be diffable across
machines." I assess it higher, for three traced reasons:

1. **`source.paths` is the s05 identity key.** Absolute, machine-/worktree-specific paths make identity
   machine-specific: a re-run from a *different* checkout path finds no `by_source` match (the recorded
   keys are machine-A absolute paths), and `by_coordinate` only holds *source-less* nodes — so a
   source-bearing node whose path doesn't match is treated as new and **re-minted as a duplicate**. That
   is precisely the re-run-duplicate fragility s05 existed to kill (the "number thing"), reintroduced
   through the path instead of the number.
2. **It's baked into the committed self-hosted store** (all 61 nodes), which is meant to be git-committed
   and CI-used. Concretely: the recorded `/Users/oubiwann/…` paths **don't resolve even inside this
   device's own Cowork VM** — I had to remap the prefix to reproduce the gate at all. That is the
   portability failure, demonstrated.
3. **s08 builds coverage-into-`check` *on* `source.paths` matching.** If the paths are absolute, that
   enforcement passes on CC's machine and breaks in CI / any other checkout — so this should be fixed
   *before* s08 builds on it, not after.

**Recommendation:** make relativizing `source.paths` to the repo root (in `migrate::resolve()` /
`build_source`) — and rewriting the 61 committed nodes via a corrective re-migration — the **first
item in s08**, ahead of the coverage-enforcement work. Not an s07 rollback: s07's rows are all met on
the machine it ran on; this is a correctness-of-the-artifact issue for the *next* consumer. CC's
disclosure was correct; I'm raising the priority, not the alarm.
