## What Worked

- **The dry-run adjudication gate did its job, twice.** Both real bugs in this slice's CLI wiring (`vision()` depending on a `source` field the project structurally never carries; `build_synthesis` not stamping schema) were caught *before* any commit reached the live store — the first by the dry-run itself failing outright, the second by the idempotence re-run explicitly required before firing. Neither bug was visible in the fixture test suite, because self-hosting a *brand-new* plan set happens to give the project a `source` at creation time (masking the first bug) and a fresh corpus has nothing to lose a schema stamp *from* (masking the second) — only the real, years-old live corpus exercised the gap. This is the concrete case for why live-run adjudication is a hard gate and not a formality.
- **Reset-and-refire, not patch-in-place.** Both times a bug surfaced against the live store, the fix went to `release/1.0.x` first (rebuilt, retested, re-clippy'd, re-fmt'd), then the store was `reset --hard` back to `2fc25f5` and the whole sequence re-fired clean, rather than hand-editing the one bad node. The final commit is a single, honest, reproducible run — not a run-plus-patch.
- **The capability/live-run split held.** Every fix this slice needed lived at the CLI call site (`crates/odm-cli/src/migrate.rs`), never inside s12's `odm-migrate` library functions (`reconcile_source`, `apply_project_vision`, `build_synthesis`) — confirming those were sound; the gap was entirely in how s13 orchestrated them.
- **Checking a "pre-existing vs. regression" question empirically, not by assertion**, for F-7: rather than assume the uncovered-doc errors were old news, spun up a disposable worktree at the exact pre-fire SHA and ran `check` against it to get a real before/after diff (0 new errors).

## Post-close correction (2026-07-30, same day)

**F-6/F-7's closing evidence was wrong — not incomplete, wrong.** The closing evidence recorded
`odm check` at "14 errors" post-fire, disclosing only the pre-existing `uncovered-doc` gap. That
count was mis-read: `check` was actually reporting **15** errors, the 15th a genuine, undisclosed
regression this slice introduced — `#1000`: `[wrong-type-field] supersedes is not a valid field on
a project node`. Per ODD-0020 §2, `supersedes`/`affects` are document-only fields, invalid on a
work node; `project` is a work type. `apply_project_vision`/`build_synthesis` sets
`edges.supersedes` unconditionally, with no type check — a latent conflict between ODD-0025 §2.3
(the project can be re-cast as a synthesis, which needs `supersedes` for lineage) and ODD-0020 §2
(work nodes can't carry it) that nothing before this slice had ever exercised on the same node
through `check`.

**Surfaced by the operator**, comparing `find docs -name '*.md' | wc -l` against `node list --all`'s
footer and asking why the counts didn't reconcile — the investigation into that question is what
caught the miscount. Confirmed the `wrong-type-field` finding is deterministic (re-ran `check`
twice, identical) and not a live-store issue (the store's own data was always correct under the
*intended* model — only the validator's rule was wrong).

**Resolved, operator-approved (Option 1 of three presented):** `check_field_validity`
(`crates/odm-core/src/check.rs`) now exempts a work node carrying `source.synthesis` from the
`supersedes`/`affects` checks — keyed on `source.synthesis`, not on `node_type == Project`, so any
future work-type synthesis is covered without a further amendment. ODD-0020 amended to **v1.4**
recording the decision; a new fixture test
(`check_permits_supersedes_on_a_work_node_re_cast_as_a_synthesis`) proves both directions. No live
store data changed — `release/1.0.x@83acedb` is a validator fix only. Re-ran `check` against the
already-committed `26bea1d` store: exactly **14** errors remain, matching the count the closing
evidence *should* have shown — the pre-existing `uncovered-doc` gap disclosed at F-7, nothing else.

**Also found in the same pass, resolved same day:** `#1000` and `#1001` both triggered a
`[no-vision]` warning ("the project states no vision — no `# Vision` section in its body"). Two
causes, two fixes (`release/1.0.x@e4508e2`): (1) `apply_project_vision`'s body never carried the
literal `# Vision` heading the old `restamp`/`with_vision` path always produced — fixed via a new
`synthesis::vision_body()` helper, shared with `replan::VISION_HEADING`; `vision()`'s idempotent
branch now re-derives and compares rather than blindly no-op-ing, so an already-minted synthesis
gets its body refreshed in place (fired live: `odm@e1e94bf`, 2 lines added, id/edges/attestation
untouched). (2) `check`'s L-3b rule iterated *every* `NodeType::Project` node — safe before the
vision mint, since there was only ever one; broke once the mint created a second (`#1001`, the
faithful 1:1 record, whose body must stay verbatim per ODD-0025 §2.1 and can never carry an
injected heading) — fixed by exempting any project node another node's `supersedes` points at.
Both were warnings, not errors; `check`'s exit code was never affected. `check` on the committed
store now shows 8 warnings (was 10), 14 errors (unchanged, the disclosed F-7 gap).
