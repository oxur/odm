## What Worked

- **Extracting `reconcile_source()` as the single policy function turned "unify two paths" into "delete one of the two implementations."** Rather than adding a second gate check to the transition path, `repair()`'s existing per-node logic moved into a shared function with a `PlanNode`/`Document` signature, and both callers now literally cannot diverge — there is no second copy of the gate/exclusion logic to drift out of sync a second time.
- **Writing the retired-node test *before* deciding whether to fix it forced the finding into the open.** Re-reading `reconcile_source`'s draft against `replan.rs`'s "a retired node is a record, not live work" principle (already established elsewhere in this codebase) surfaced that `self_host`'s `by_coordinate` map had no retired guard at all — the same *shape* of gap CDC found for the project node, just undiscussed. Worth naming as a general review technique: when unifying two paths around one invariant, check the unified function against *every* precedent invariant this codebase already established nearby, not just the one named in the bug report.
- **The end-to-end CLI fixture test (F-4) as a single test function, not four, kept the assertions honest.** Building one fixture with all four shapes (stub, faithful, synthesis-project, missing arc) in one store and walking every node's outcome after one `odm migrate` call caught the ordering/wiring correctly the first time, because a bug in either stage (repair or import) would have shown up as a wrong assertion on a *shared* fixture rather than being isolated away into stage-specific fixtures that couldn't interact.
- **Testing the "order is load-bearing" claim empirically (by reasoning through both orderings) rather than accepting it on the plan's authority caught a real nuance** (see F-3's note and the closing report) without requiring any scope change — the implementation still does exactly what was asked; only the *justification* recorded for it is more precise than the plan's framing.
